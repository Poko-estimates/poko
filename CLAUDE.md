# Poko

pnpm workspace: `frontend/` (Next.js 16 App Router) + `backend/` (Supabase project).
Node 22, pnpm 10.18.1 — pinned via `packageManager`, don't use npm or yarn.

## Commands

Run from the repo root; both packages are reachable through root scripts.

```bash
pnpm dev / build / lint     # frontend
pnpm db start|stop|reset    # local Supabase stack (needs Docker)
pnpm db migration <name>    # new timestamped migration
pnpm db gen:types           # regenerate frontend/lib/supabase/database.types.ts
pnpm db test:db             # pgTAP
```

Before calling work done, run what CI runs for the half you touched:
frontend → `pnpm lint`, `pnpm exec next typegen`, `pnpm exec tsc --noEmit`, `pnpm build`;
backend → `pnpm db reset` (applies every migration from scratch) and `pnpm db test:db`.

## Architecture rules

- **RLS is the authorization boundary, not the query.** Queries deliberately omit
  `where user_id = ...`; a policy already limits the rows. Never add a filter as a
  substitute for a policy, and never trust `user_metadata` for an access decision.
- **Reads** live in `lib/<area>/queries.ts` as plain async functions called directly
  from server components — not server actions, which would cost a round-trip.
- **Writes** live in `lib/<area>/actions.ts` behind `"use server"` and return
  `{ formError?: string }` for the form to render; they don't throw at the UI.
  Queries may throw. Call `revalidatePath` after anything a page renders.
- **Privileged mutations go through security-definer RPCs**, not table writes:
  `start_round`, `close_round`, `join_issue`, `reorder_issues`, `delete_sprint`, …
  Columns the client must not set (`owner_id`, `slug`, the clock columns) are held
  out of every grant on purpose. If a write needs a column you can't reach, write a
  migration with a routine — don't widen the grant.
- **Realtime payloads are thin.** Broadcasts are unfiltered by RLS, so they say
  "something happened" and the client refetches. Don't put row data in one.
- `proxy.ts` is Next 16's renamed middleware and keeps the Supabase session fresh.
- Supabase clients: `lib/supabase/server.ts` per request (never hoist to a module
  global), `lib/supabase/client.ts` in the browser (already a singleton).

## Database

- Migrations are forward-only. Never edit one that's been applied — add a new one.
- Every migration opens with a comment explaining *why* the shape is what it is,
  including the consequences a future reader would otherwise trip over.
- New table ⇒ RLS enabled, explicit policies, and an index on each FK.
- Add pgTAP assertions in `backend/supabase/tests/` for anything that could fail
  *silently* — wrong rows visible, a guard that stops guarding.
- `database.types.ts` is generated. Regenerate after schema changes; never hand-edit.
- `seed.sql` is local-only by design (it refuses to run against a non-default JWT
  secret). Keep that guard.

## Frontend conventions

- Double quotes, no semicolons, kebab-case filenames, named exports, `@/*` imports.
- Server components by default. `"use client"` only for the subtree that needs
  interactivity — e.g. the once-a-second timer is its own component so nothing else
  re-renders at that rate.
- Tailwind v4, CSS-first: tokens live in `app/globals.css` `@theme`. There is no
  `tailwind.config`. Style with semantic tokens (`bg-primary`, `text-muted-foreground`,
  `border-border`) and compose classes with `cn()` — no raw hex, no ad-hoc colors.
- `components/ui/` is generated shadcn (`base-nova` style) on top of `@base-ui/react`,
  **not** Radix. Prefer `pnpm dlx shadcn@latest add <component>` to hand-rolling, and
  keep local edits to those files minimal. Icons: `lucide-react`.
- Interactive elements carry the accessible name/role (`role="timer"`, `aria-label`)
  the existing components model.

## Reviewing

Use the `poko-review` skill (`.claude/skills/poko-review/`) for any review of
this code — a diff, a PR, a migration, or a full sweep. It covers the database
boundary, where mistakes fail silently: the revoke-then-grant rule, RLS and
security-definer obligations, the blind-vote guarantees, and session handling.
Everything else is ordinary review against the rules above.

## Comments

This codebase comments the *reasoning*, not the mechanics: the race the retry exists
for, why a column is derived rather than stored, what breaks if the check is removed.
Match that. Don't narrate what the line already says.

## Git

Two long-lived branches: `dev` is staging, `main` is production.

- Branch off `dev`, and open every feature or fix PR against `dev`.
- `main` only ever takes a PR from `dev` — that merge is the release.
  Never PR a feature branch straight into `main`, and never push to either directly.

Never commit `.env*`.
The `frontend/AGENTS.md` block is regenerated by `next dev` — commit it with your work
rather than reverting it.
